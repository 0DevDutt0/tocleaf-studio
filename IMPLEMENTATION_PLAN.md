# Implementation plan

Status key: **done** (acceptance criteria tested), **in progress**, **not started**.
Dates: 10 Nov 2026. Each phase lists what was verified and what remains. Results are recorded in
`PROJECT_STATUS.md`.

## Phase 0: research and compatibility: done

Exit criterion: the upstream pipeline can be invoked, and every blocker is documented.

- Paper analysed: `docs/research/STAIR_PAPER_ANALYSIS.md` (leaf-formula inconsistency and missing details recorded).
- Upstream audited at `3729c54`: `docs/research/UPSTREAM_IMPLEMENTATION_AUDIT.md`. No licence, so the upstream is kept
  outside the repository (ADR-001).
- Upstream runs: `stair --help` and every subcommand's help, the upstream test suite (122 passed), a bf16 CUDA kernel,
  and an end-to-end training run on this project's fixture data (see PROJECT_STATUS.md).
- SearchTome audited per domain: `docs/research/SOURCING_AND_DATA_AUDIT.md`. The public release does not match the paper's
  benchmark, so no reproduction claim is made.
- Architecture recorded: `docs/architecture/INITIAL_ARCHITECTURE.md`, `ARCHITECTURE_DECISIONS.md`.

## Phase 1: core STAIR vertical slice: in progress

Exit criterion: a query produces a valid leaf-node result using a trained model, mapped to the correct section.

| Step | Status | Evidence |

| Real training with the pinned upstream trainer | in progress | fixture-r4 run (see PROJECT_STATUS.md) |

| Valid-leaf retrieval result mapped to the section | pending training | |

Remaining Phase 1 work:

1. Read the fixture-r4 result: loss curve, peak GPU memory, adapter saved, boundary warnings.
2. Run `stair report-train` (upstream) on the run, to verify the upstream report command works here.
3. Run our evaluation: `eval-stair` (constrained, unconstrained, unconstrained with the upstream prompt) and `eval-bm25`,
   then the upstream `stair eval` smoke test for comparison.
4. Pick one real, legally usable test document with a nested ToC (candidates in `SOURCING_AND_DATA_AUDIT.md`), and
   repeat the pipeline on it. The fixture alone is not enough evidence.

## Phase 2: evaluation and baselines: not started (partly implemented)

- Done: metrics (recall, hit, MRR, nDCG, invalid, non-leaf, wrong-retrieval rates), BM25 baseline, per-query output.
- Not started: dense baseline (local `nomic-embed-text` or `qwen3-embedding:0.6b` through Ollama), DSI-style control (no
  ToC input), a human-written evaluation set with gold leaves, significance testing, and the constrained-versus-
  unconstrained comparison on a corpus large enough to support it.
- Paper's Recall@1 dev-based early stopping: not wired (ADR-011).

## Phase 3: STAIR-Hybrid: not started

Passage retrieval inside the routed section, BM25 and dense fusion, optional reranking, grounded answers with
citation verification and abstention. Starts only after Phase 2 exit criteria pass.

## Phase 4: frontend: not started

FastAPI backend, SQLite metadata, persistent jobs, and the six screens. The user's frontend workflow applies (design
system, Playwright review at 375, 768 and 1440 px, axe-core), which is set up when this phase begins.

## Phase 5: advanced: not started

Multi-document routing, human evaluation, better ToC extraction, document versioning, multi-hop retrieval (bounded),
dynamic ToC construction. Each is an experimental extension.

## Phase 6: release readiness: not started

Testing, profiling, error handling, documentation, screenshots, licence decision (ADR-009), installation instructions,
and a README that separates the paper's method from this project's extensions.
